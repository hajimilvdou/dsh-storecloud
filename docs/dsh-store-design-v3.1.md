## S1. 供应链安全纵深

### S1.0 资源问题（直接回答）

**不需要大量服务器资源。** 关键在三个设计：

| 设计 | 效果 |
|---|---|
| **事件驱动，不做全量轮扫** | 只在"新收录 / 版本变更"时触发扫描。库内 286+ 插件，每日变更通常个位数——每天扫几个包，不是每天扫全库 |
| **分层扫描，重层按需** | 见下表：L0~L2 是纯静态分析，单包耗时秒级；L3 动态沙箱只对"高风险信号包 / 被举报包 / 冲榜异常包"触发 |
| **结果缓存** | 扫描结果以 `包名+精确版本` 为 key 入库，同版本永不重扫；2C4G 单机绰绰有余 |

### S1.1 四层扫描管线

| 层 | 内容 | 单包成本 | 触发时机 |
|---|---|---|---|
| **L0 元数据信誉** | 作者账号年龄、仓库存在性、周下载量、license、是否 fork | ≈0（抓取层顺带） | 收录时 |
| **L1 包级静态检查** | 下载 npm tarball（通常 <1MB）→ 检查 `package.json` 的 **preinstall/install/postinstall 脚本**（供应链攻击重灾区）→ 依赖树比对 OSV 漏洞库（API 调用，零自建成本）→ 文件清单（是否含二进制/.node 原生文件） | 秒级 | 收录 + 每次版本变更 |
| **L2 代码模式扫描** | 静态规则扫危险模式：`child_process`/`eval`、可疑外联域名、混淆代码特征、读取敏感环境变量（`*KEY`/`*TOKEN`） | 秒级 | 同 L1 |
| **L3 动态沙箱（可选，后置）** | 隔离环境实际安装并观察行为 | 分钟级 | **仅**高风险信号 / 被举报 / 榜单异常飙升 |

### S1.2 结果使用

- 每个插件产出 **安全分 + 风险标签**（如"含 install 脚本""含原生二进制"），卡片徽标展示，安装确认清单中醒目标注；
- **不阻断、只透明**（默认）：低风险照常安装，高风险要求用户勾选"我已知晓"；
- **恶意包拉黑（管理端）**：一键拉黑后写入下发数据，**客户端安装器强制拦截**（这是唯一硬阻断），全客户端下次心跳生效。

## S2. 已安装台账 · 还原点 · 更新通知体系

### S2.1 本地已安装台账（登录与否都有——数据在本地）

插件安装器每次操作写入台账（本地存储）：

`记录项 = { 插件包名, 安装版本, 安装时间, 来源(组合ID | 单独安装), 归属组, 还原点ID }`

- **组合安装**：台账记一条组记录 + 各成员记录（成员归属组）；
- **还原点**：每次安装/升级/卸载前，自动快照 `cordis.patch.yml` + 当前版本清单。还原点保留 N 个（可配置，默认 10）。

### S2.2 用户页（"我的"）信息架构

```
我的
├── 🔔 通知中心（顶部常驻，见 S2.4）
├── 🗂 已安装·插件组
│    └── 每组卡片：组名 / 成员数 / 订阅状态 / 更新徽标（两种）
│        操作：[一键更新] [回退到还原点] [一键卸载整组]
├── 🧩 已安装·单独插件
│    └── 默认折叠（数量多），提供搜索框
│        ⚠️ 有更新的单个插件自动从折叠中浮现到本区顶部
│        每条操作：[更新] [一键卸载]
└── ⚙️ 设置…
```

### S2.3 更新检测（纯本地计算，零网络）

插件/组数据通道已把"最新版本"下发到本地，检测只是本地比对：

| 检测 | 比对 |
|---|---|
| 单个插件有更新 | 台账版本 < 本地索引中的最新版本 |
| 组内插件有更新 | 同上，且成员归属组 → **组卡片与单插件区同时显示**（双维度都提醒） |
| 组作者新增插件 | 订阅组的本地快照 hash ≠ 通道下发的组 hash → diff 出新增成员 |

### S2.4 通知系统（硬要求：通知必带定位，禁止"只说有更新"）

**双角标语义（悬浮球）**：

| 角标 | 含义 | 来源 |
|---|---|---|
| 🔴 `!` | 公告 | 管理端手动发布 |
| 🔵 数字 | 更新/待办（可更新数 + 待确认上报数） | 本地检测产出 |

**通知中心条目规则**：
- 每条通知 = **图标 + 一句话说清"什么变了" + 可点击定位**；
- 点击 → 自动跳转到对应组卡片/插件条目并**高亮闪烁**——用户永远知道"变动在哪"；
- 组内插件更新的通知，文案同时说明归属：`「新手启航包」成员 dsh-memory 有更新 v0.3.1 → v0.4.0`；
- 通知不自动消失原则：只有用户执行（更新/忽略）后才清除。

## S3. 组详情查看与订阅模型

### S3.1 组卡片展开

- 组合页/已安装组卡片可展开 → **成员插件列表：每个成员显示名称 + 简介（2 行）+ 版本 + 更新徽标**；
- 成员可点击进插件详情（复用搜索结果的详情卡）；
- 成员前有勾选框 → **选择性安装**。

### S3.2 订阅语义（核心规则）

| 安装方式 | 归属组 | 订阅 | 后续"作者新增插件"通知 |
|---|---|---|---|
| **一键安装整组** | ✅ | ✅ 默认订阅 | 会收到 |
| **选择性安装部分成员** | ✅（台账记归属组） | ❌ 默认不订阅 | **不收**——安装时明确提醒 |

选择性安装确认弹窗文案（要点）：
> "你正在从「XX 组」选择性安装 N 个插件。**未订阅该组**：作者后续新增插件时将不会通知你。如需接收，可在安装后点 [订阅插件组]（一键安装整组则默认订阅）。"

- 订阅关系存本地（`subscribed: 组ID → 上次所见组快照hash`）；登录用户可选择云同步订阅关系（跨设备，登录体系的兑现点）；
- 已安装组卡片上常驻 [订阅/退订] 切换。

## S4. 初始扫描与遗漏插件上报

### S4.1 首次扫描（插件装好后首次启动 + 每次数据同步后增量复查）

```
读取本地插件树（cordis.patch.yml + node_modules）
  → 过滤官方框架包（@deepseek-ai/* 白名单——它们是框架本体不是"插件商品"）
  → 与本地索引比对
  → 命中库外 → 进入"待确认上报"清单
```

### S4.2 上报询问（通知中心，不弹窗骚扰）

- 通知中心出现询问卡片："发现 N 个库外插件（可能是你自行安装的），是否上报以帮助收录？"
- **逐个列出**（名称 + 本地路径来源），每个可单独选 [上报] / [否]；
- 上报内容最小化：包名 + 仓库地址（若 package.json 里有 repository 字段）+ 版本，**不含任何本地路径与代码**；
- 选"否"即永久不再询问该项（本地记忆）。

### S4.3 管理端：上报队列 + 提速收录框

| 功能 | 说明 |
|---|---|
| **上报队列页** | 管理员可查看、搜索所有用户上报的库外插件（聚合去重，显示上报人数作为收录优先级信号） |
| **单独提速收录框** | 管理员输入 GitHub 仓库地址 → **立即单条触发提取管线**（不等每日同步）→ 分钟级入库并进入正常下发 |
| 判定 | 上报项可标记"已收录（自动关联）/ 无效 / 拒绝"，已收录的自动从队列归档 |

防滥用：上报接口限流（按用户/IP），管理端可封禁恶意上报者。

## S5. 配置与 API 增补

**配置中心新增**：`security.scan_level`（默认 L2）、`security.blocklist`（拉黑列表）、`restore.max_points`（默认 10）、`notify.badge_enabled`、`report.rate_limit`。

**API 新增（写，登录）**：`POST /api/v1/reports/missing`（库外插件上报）。
**管理端新增**：上报队列 CRUD、`POST /admin/fast-track`（提速收录）、安全扫描结果查询、拉黑管理。

## S6. ADR 增补

| 决策 | 结论 | 理由 |
|---|---|---|
| 扫描策略 | 事件驱动 + 分层 + 缓存 | 全量轮扫浪费 99% 资源；变更才扫，2C4G 足够 |
| 硬阻断范围 | 仅"已拉黑包" | 其余用透明标注，避免误杀正常插件 |
| 更新检测 | 纯本地比对 | 数据通道已含最新版本，零网络、离线可用 |
| 订阅默认 | 一键装组=订阅；选择性装=不订阅+明示 | 知情权在用户，避免"悄悄订阅" |
| 官方包过滤 | `@deepseek-ai/*` 白名单不参与库外上报 | 它们是框架本体，不是待收录商品 |
| 通知哲学 | 每条通知必须可点击定位到变动处 | "只提醒不指路"等于没提醒 |
